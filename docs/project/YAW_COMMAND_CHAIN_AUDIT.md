# Yaw 速度命令与闭环检查（2026-09-17）

本轮按用户要求检查目标传入，保留控制代码和PID。当前磁盘内环360/0/0、输出限6000、
协议限12000、手动100度/秒、速度单环；此前匹配板上ELF b3843d5f也为这组参数。
本轮未连接硬件，不能把主机测试当作当前实车稳定性验证。

## 发现：快速反向输入可能持续保留旧方向

`application/cmd/command_router.c:132`把与`previous_yaw_input`相差超过1000的输入
替换为旧值；函数末尾又把这个替换后的值保存为历史。它没有等待新帧确认或超时机制。

真实生产链主机复现（4ms控制步长，反馈在线、普通手动）：

| 输入操作 | 应有速度目标 | 实际传入PID |
|---|---:|---:|
| ch0=-660保持 | +16.667 RPM | +16.667 RPM |
| 下一输入ch0=+660，并保持1000ms | -16.667 RPM | 持续+16.667 RPM |
| ch0=0被接收后，再ch0=+660 | -16.667 RPM | 恢复-16.667 RPM |

这个过滤器将合法的1320刻度反向跳变当成异常。触发条件是实际接收/路由序列发生大跳变，
不是每次快速推杆都必然触发；若接收到了足够的中间杆量，就不会卡住。
消息中心忠实发布了被过滤后的旧值，PID也忠实使用了它，错误位于路由目标生成。
从此前匹配板上的ELF反汇编也确认存在该分支，不只是未烧录的磁盘代码。

建议修复方向：不要无限保留旧输入。合法范围内的反向命令应能被接受；若保留异常跳变保护，
必须按新的遥控帧确认候选并有明确的超时/失效行为，不能按重复控制回调充当多帧确认。
本轮仅检查，未替用户选择过滤策略或修改运动行为。

## 遥控输入为何会滞留

从原始18字节DBUS帧补充验证，链路各层的状态如下：

| 阶段 | 实际行为 | 与滞留的关系 |
|---|---|---|
| USART3 DMA/IDLE/TC→BspRc_OnRxEvent | 上游解码；桥接只有完整18字节事件才通知应用 | 半帧不发布新电机命令，原命令暂保留直到新完整帧或应用超时 |
| DBUS解码→NyushRemoteSnapshot→on_frame | ch0解码减1024，越出±660归0；复制ch0/拨杆，计帧并发布RC_UPDATE | 合法反向值能正常通过，解码层没有本次无限保留旧杆量的逻辑 |
| RC_UPDATE最新槽→CmdController.on_rc_update | 按值复制，只保留尚未派发的最后一份；接收回调复制到s_input | 同一派发前的中间回中值可能被合并，路由不能假设看见每一帧 |
| CmdController_Task | 消费更新标志并更新时间；200ms内保持最近输入，CAN未解锁时禁用 | 新帧不断到达即保持在线，不检查路由是否接受新杆量 |
| route_gimbal | 取反/死区后与最后接受值比较，差>1000则回退，回退值又保存为历史 | 新反向帧持续到达仍反复被拒绝，是无限滞留的直接原因 |
| GIMBAL_CMD→速度PID→CAN电流 | 发布过滤后的yaw_rate；换算RPM后计算速度误差、电流并发送 | 下游每轮正常执行错误的旧目标；目标平稳不证明符合原始杆量 |

例如最后接受的yaw_raw=+660，新输入yaw_raw=-660：差1320，被替换成+660，
previous_yaw_input又写回+660。下一次比较仍是同一差值，不会因持续收到新帧而自动恢复。
阈值是严格大于1000，边界1000接受、1001拒绝。任何合法历史值到0的差至多660，
因此只要回中值真正进入路由，就会解除这种滞留；短暂经过中间位置不等于被路由消费。

补充原始帧实验使用真实串口桥接/上游解码/消息中心/Cmd/Router，结果：

- 连续50帧、700ms均解码ch0=+660，帧计数推进、gimbal.enabled为1，yaw_rate仍+1，
  本应-1。证明“遥控在线且新帧正常”与“路由目标卡住”可以同时成立。
- 已接受ch0=-660后，在下一次派发前注入ch0=0、再ch0=+660，中间回中帧被最新槽合并；
  路由看到大跳变并保留旧目标。是可复现触发条件，未证明实车异常时发生过该合并。
- 超过200ms无帧会禁用并清空当前输出/gimbal_memory，但离线分支没有清空
  previous_yaw_input。保持CAN已解锁的测试中，重新收到相反端点后会再次保留掉线前方向。
  停机窗口本身仍为零输出；不能把残留历史描述为掉线期间继续出力。
- 越界ch0=700在上游解码归0，目标也归0；不是把非法输入保留成旧非零目标。

此外，上游约100ms守护清的是解码器自己的缓存，不会主动发布零RC_UPDATE；应用缓存
由独立200ms超时保护。它解释断流后的短时保持，不解释新完整帧持续到达时无限拒绝反向。
CmdController的在线时间记录在消费新消息时，而不是串口到达时；未实测卡顿下的时间偏差。
main先Task后Dispatch带来的一轮输入延迟、遥控两帧间正常保持，也都与该无限拒绝问题分开。

修复应同时处理正常反向输入的接受、过滤器历史在失效/恢复时的重置，以及新遥控帧身份。
不能只调大阈值或重复主循环确认次数来掩盖“最后接受值永不前进”的问题。
如需要平滑运动，可在目标生成后另按dt限加速度，合法新目标仍应被记住。

## 其余链路的验证结果

路径为解码RC消息→CmdController→CommandRouter→TOPIC_GIMBAL_CMD最新槽→云台回调→
速度PID→电机服务→DJI适配器→CAN管理器→CAN1/0x2FE槽0。CAN1/0x209反馈经真实解析和
消息回调更新同一软件ID5的上下文，速度为有符号RPM。

- 遍历全部1321个合法ch0值（以小步变化避免上述过滤器），实际PID目标均符合
  `-deadband(ch0)/660*100/6`，满杆约±16.667RPM。目标限30RPM，不是满杆必到30RPM。
- 反馈-120～115RPM扫动且遥控回中时，PID目标始终0；误差始终为目标减反馈。
  反馈不改写目标，速度单环没有位置PID参与，也没有服务层二次计算PID。
- 消息载荷按值复制；发布后修改发送缓冲区不改变接收结果。每轮注入400条普通事件造成
  普通队列覆盖，云台最新命令仍送达，其覆盖/拒绝计数均0。
- 真实冻结main先执行CmdController_Task，再MsgCenter_Dispatch；本轮派发的新遥控消息
  在下一轮才参与目标生成。测试确认是一轮延迟，不是丢命令；实机延迟取决于主循环耗时，
  不能把测试4ms当作固定实机周期。冻结main未修改。
- 模拟每16ms才来一帧遥控、每4ms控制时，中间继续保持上一有效杆量，不会误归零。
  遥控超过200ms未更新后发布禁用，重新收到遥控并完成稳定反馈等待后恢复。
- speed_loop_only下spin/有效vision显式强制速度目标0，普通模式恢复杆量目标；这属于现行
  调试模式规则，不能按位置控制模式的语义期待其跟随。
- 按真实PID验证目标0/反馈+10RPM时的比例制动、2ms输出低通历史、6000输出限、整数转换；
  最终真实CAN打包值与监控请求逐次一致。协议12000不会扩大PID已经限到6000的请求。

## 与现有抖动日志的关系

16:03开始的logger记录中，约16:06:13目标95.6～96.1度/秒而反馈-528～690度/秒，
约16:06:08目标全0而反馈-720～480度/秒。目标来自PID实际采用值，单位均为度/秒。
日志没有对应的原始ch0，目标平稳也可能是上述过滤器保留旧值，不能仅据目标平稳排除
输入生成问题。但是目标已经为0的剧烈反馈不能由“持续保留非零旧方向”单独解释。
需要同步原始ch0、路由yaw_rate、PID target/actual、电流请求、反馈时效和控制dt，才能
确定本次运动是否触发过滤器，以及目标正确时的剩余振动原因。

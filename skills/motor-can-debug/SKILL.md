# 电机 CAN 调试

将问题逐段定位到电脑链路、转发设备、CAN 总线、协议或电机执行。优先沿用用户选定
的链路与项目；无需达妙助手也可经匹配 SDK/串口协议发送 CAN。不要把设备检测成功、
CAN 发送成功与电机执行成功混为一谈。

## 选择链路

- **ST-Link → C 板 → CAN**：读 [references/cboard-rtt.md](references/cboard-rtt.md)。
  本仓库 `Diagnosis` 分支的主机接口是 **RTT 通道 0 双向终端**，支持发原始 CAN、
  读取 CAN 接收回调事件与错误状态。不要换回主机周期扫描自定义 RAM 邮箱的方案。
- **电脑 → USB-CAN → 电机**：读 [references/usb-can.md](references/usb-can.md)。
  区分原生 dm-device-sdk 设备与 HDSC CDC 串口固件；相同板卡外观不能决定后端。
- **无回复、发送失败、数值可疑或停止确认**：按需读
  [references/troubleshooting.md](references/troubleshooting.md)。
- **这台机器的路径、已验证型号和实测边界**：读
  [references/verified-setup.md](references/verified-setup.md)。这些是参考配置，接入前重新核对。

## 执行约定

1. 确认用户要只读诊断、修改固件/参数，还是实际使能/运动。检查已有控制进程和
   连接占用；写文档、蒸馏或安装 skill 不等于启动/停止正在运行的电机。
2. 读取目标仓库的 `AGENTS.md` 与当前硬件/构建文档。只读查询不用重复索要许可；
   烧录、修改模式/参数和运动须在用户已经授权的范围内进行。已有明确授权继续适用，
   skill 本身不是以后任务的永久操作授权。
3. 确认 C 板、转接器与电机供电及 H/L/地连接。ST-Link 显示 MCU 约 3.3 V 不证明
   CAN 收发器已完整上电。USB 转接器被识别也不证明电机已供电。
4. 先用匹配的只读参数查询确认实际 ID、反馈 ID、波特率/模式和反馈范围。未知型号、
   控制协议、CAN FD 设置和物理限值保持不支持，不套用 J3507 数值。
5. 用新鲜度与原始报文验证：保存发送内容、完成结果、接收 ID/载荷及接收计数/时间。
   缓存默认值 `0` 不能作为收到反馈的证据。每个 RTT 请求使用新的 token。
6. 已授权运动时，优先使用已验证的有监测控制程序；模式切换后读回确认，发送零速
   后再使能，持续检查新反馈和实际状态，退出时分别尝试零速和失能。连接丢失时
   无法保证停止帧送达；只报告确实观察到的结果。
7. 用户要求停止时，优先停止正在发送的控制进程，再核对新鲜失能反馈；不要让一个
   循环继续写速度、另一个客户端不断发失能。使用当前 PID，不复用历史 PID。

## 验证与交付

- 区分源码/编译、无硬件测试、板上烧录校验、真实 CAN 收发和实际运动观察。
- 只读接入以匹配的电机应答闭环；RTT hello 或内部回环不能替代外部 CAN 验证。
- 运动以持续变化的角度与合理时间差验证；低速瞬时速度存在量化，不能只看一个样本。
- 停止以新收到的失能状态确认；只有发送完成时说“停止命令已发出”，无回复时说未确认。
- 报告当前是否仍在运行、如何停止、采用的链路及实际参数。记录可复用结论，不把
  一次现场 PID、端口号、旧板上状态或任意一段历史日志当作永久配置。
